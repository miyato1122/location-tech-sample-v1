# 位置情報テクノロジーサンプル（Spec Kit CC）憲法

## コア原則

### I. 仕様書ファースト

すべての機能は仕様書（`spec.md`）の作成・レビュー・承認から始まる。
実装はユーザーストーリーと受入条件が仕様書に記述され、承認されるまで開始してはならない（MUST NOT）。

- 仕様書は `/speckit-specify` コマンドで生成する
- 仕様書には「ユーザーストーリー」「機能要件」「成功基準」「前提条件」を含めなければならない（MUST）
- 実装計画（`plan.md`）は仕様書から導出する
- 仕様書なしの場当たり的なコード追加は禁止（MUST NOT）

**根拠**: 仕様が曖昧なまま実装すると手戻りが発生する。
仕様書を先に固めることで、実装の方向性を合意してから着手できる。

### II. 地図・位置情報中心設計

本プロジェクトは MapLibre GL JS を中核とする地図ビジュアライゼーションアプリケーションである。
設計はこの中心的な役割を常に反映しなければならない（MUST）。

- 地図レンダリングには MapLibre GL JS を使用する（MUST）
- データソースはラスタータイル・ベクタータイル・GeoJSON のいずれかを使用する（MUST）
- 地理空間演算には @turf/* ライブラリを優先して使用する（SHOULD）
- レイヤーの表示制御には maplibre-gl-opacity を使用する（SHOULD）

**根拠**: 技術スタックを統一することでコードの一貫性を保ち、
学習コストを最小化する。

### III. 最低限テスト

テストは必要最低限に留める。テスト駆動開発（TDD）は本プロジェクトでは必須としない。

- コア機能の動作確認には受入テストを書く（SHOULD）
- 単体テスト・統合テストはユーザーが明示的に要求した場合のみ作成する（MUST, 要求がない場合は省略可）
- タスクファイル（`tasks.md`）にテストタスクを含める場合は明示的に要求があった場合のみとする
- ブラウザでの目視確認（手動テスト）を主要な検証手段として許容する

**根拠**: 地図アプリケーションはブラウザでの目視確認が最も効果的であり、
過度なテスト自動化は開発速度を下げる。

### IV. 日本語ドキュメント

すべてのドキュメント・仕様書・コードコメントは日本語で記述しなければならない（MUST）。

- `spec.md`・`plan.md`・`tasks.md` など `.specify/` 配下のドキュメントは日本語で作成する（MUST）
- ソースコード内のコメントは日本語で記述する（MUST）
- コミットメッセージはプレフィックス（`feat:`, `fix:` 等）を英語とし、本文を日本語にする（SHOULD）
- 変数名・関数名・クラス名などの識別子は英語のまま維持する（MUST）

**根拠**: プロジェクトチームの母国語が日本語であるため、
日本語での記述が理解・レビューの効率を高める。

### V. シンプルさ優先

機能が正しく動けば十分。過剰な抽象化・将来の拡張への備えは行わない。

- YAGNI（You Aren't Gonna Need It）原則を適用する（MUST）
- 3箇所以下の類似コードに抽象化を導入してはならない（MUST NOT）
- 1ファイル・1責任を基本とするが、小規模な機能は同一ファイルに収めてよい
- 依存ライブラリの追加は既存の `package.json` で解決できない場合のみ行う（SHOULD）

**根拠**: 地図サンプルアプリケーションの教育的価値は
シンプルなコードで概念を伝えることにある。

## 技術スタック要件

本プロジェクトで使用する技術スタックを以下に定める。
追加・変更は Governance セクションに従い憲法改正手続きを踏む。

- **言語**: JavaScript (ES Modules)
- **ビルドツール**: Vite
- **地図ライブラリ**: MapLibre GL JS
- **地理空間演算**: @turf/*
- **UI制御**: maplibre-gl-opacity
- **地形データ**: maplibre-gl-gsi-terrain（国土地理院標高タイル）
- **ターゲット環境**: モダンブラウザ（Chrome・Firefox・Safari 最新版）

## 開発ワークフロー

機能追加・変更の標準手順を定める。

1. `/speckit-specify` で仕様書を作成・レビュー・承認する
2. `/speckit-plan` で実装計画を作成する
3. `/speckit-tasks` でタスクリストを生成する
4. `/speckit-implement` でタスクを順番に実装する
5. ブラウザでの動作確認を実施する
6. 必要に応じて `/speckit-git-commit` でコミットする

**ブランチ戦略**:

- 機能ブランチ名は `NNN-機能名-kebab-case` 形式を使用する（SHOULD）
- メインブランチへのマージ前にブラウザ確認を完了させる（MUST）

## Governance

本憲法はプロジェクトの開発指針の最上位文書である。
他のすべての慣行・慣習はこの憲法に従う。

**改正手順**:

1. 改正案を記述し、影響を受けるすべてのテンプレートへの波及を確認する
2. `/speckit-constitution` コマンドを使用して憲法を更新する
3. バージョンをセマンティックバージョニングルールに従い更新する
4. 変更をコミットし、影響を受ける仕様書・計画書を更新する

**バージョニングポリシー**:

- MAJOR: 原則の削除・後方互換性のない再定義
- MINOR: 原則・セクションの追加または実質的な拡張
- PATCH: 文言の明確化・誤字修正・表現の微調整

**コンプライアンス確認**:

- PR レビュー時には憲法への準拠を確認する（SHOULD）
- 新機能開発前に Constitution Check（`plan.md` 参照）を実施する（MUST）
